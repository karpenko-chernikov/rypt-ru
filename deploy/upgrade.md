## 5. DB migration test (2026-11-08) — pre-existing bug found

Applying migrations to a copy of the local DB fails IDENTICALLY on BOTH
Wagtail 6.4.2 and Wagtail 7.4.4 at
`home.0023_convert_contacts_to_contactspage`:

    sqlite3.OperationalError: no such table: home_trainingboardpage

Root cause: `0023` imports live models and calls `old.delete()`; Wagtail's
page-deletion cascade touches `home_trainingboardpage`, but that table is
created only in `home.0024` (which depends on `0023`). A fresh `migrate`
(empty DB, or a DB older than `0024`) therefore fails.

Impact:

- PRE-EXISTING, independent of the Django/Wagtail upgrade (confirmed on both).
- The local dev DB is stale: `home` migrations 0016-0028 are unapplied, which
  is why the failure surfaced locally.
- A fully-migrated production DB is unaffected by this specific crash; the
  upgrade adds only 7 additive Wagtail migrations: `wagtailadmin.0006`,
  `wagtailcore.0095/0096/0097`, `wagtailsearch.0009/0010`,
  `wagtailusers.0015`.
- The Dockerfile CMD runs `manage.py migrate` on every start, so a fresh
  environment/DB would crash today — a deployability landmine.

Proposed fix (separate task): reorder dependencies so the TrainingBoardPage
table exists before the page-deletion cascade runs:
`home.0024` depends on `home.0022` (instead of `0023`), and `home.0023`
depends on `home.0024`. Alternatively rewrite `0023` to use historical
`apps.get_model()` models instead of live imports.

## 8. Production deploy + rollback (bare-metal)

Production does NOT use Docker. Deploy mechanism:
`deploy/bootstrap.sh` (`sudo deploy/bootstrap.sh [SRC]`):

1. rsync source to `/srv/rypt/releases/<timestamp>`
2. fresh venv + `pip install -r requirements.txt` (now pinned)
3. `collectstatic` into `$REL/static`
4. stop `rypt`, run `manage.py migrate` (runtime user)
5. atomically switch `/srv/rypt/current` symlink, install systemd unit + nginx,
   restart

Pre-upgrade DB snapshot (run before any deploy):

    sudo systemctl stop rypt
    sudo cp -a /var/lib/rypt/db/db.sqlite3 /var/lib/rypt/db/db.sqlite3.pre-upgrade
    sudo cp -a /var/lib/rypt/db/db.sqlite3-wal /var/lib/rypt/db/db.sqlite3-wal.pre-upgrade 2>/dev/null || true
    sudo cp -a /var/lib/rypt/db/db.sqlite3-shm /var/lib/rypt/db/db.sqlite3-shm.pre-upgrade 2>/dev/null || true
    sudo systemctl start rypt

Rollback (code):

    sudo deploy/rollback.sh   # swaps current/previous symlinks, restarts rypt + nginx

Rollback (DB, only if the additive migrations cause problems):

    sudo systemctl stop rypt
    sudo cp -a /var/lib/rypt/db/db.sqlite3.pre-upgrade /var/lib/rypt/db/db.sqlite3
    sudo rm -f /var/lib/rypt/db/db.sqlite3-wal /var/lib/rypt/db/db.sqlite3-shm
    sudo systemctl start rypt

`deploy/rollback.sh` is forward-only for the DB (it does NOT undo migrations).
The new Wagtail migrations are additive (create table/index/column), so the old
6.4.2 code normally tolerates them; restore the DB snapshot only if behaviour
regresses.
